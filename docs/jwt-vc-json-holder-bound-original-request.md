# VC1.1 jwt_vc_json holder-bound original verifier request (opt-in)

This SDK-only HeroSSID extension to the bounded OpenID4VP 1.0 `jwt_vc_json` direct_post flow requires the Wallet holder's actual Ed25519-signed VP to include `herossidRequestSha256`: lowercase SHA-256 of the **exact compact signed verifier Request Object**. The verifier must separately retain that original signed request and its digest under its own trusted challenge/tenant state, not read the pin from the form, VP or caller.

The Wallet independently pins the verifier DID, HTTPS callback, trusted issuer, credential type and HTTPS subject vocabulary, checks the issuer's original JWT, displays every disclosed claim, obtains actual application-layer consent and then calls `OpenId4VpJwtVcJsonDirectPost.CreateHolderBoundResponseForm`. The verifier calls `CheckHolderBoundResponseForm` with its own retained SHA-256, exact signed request and independent pins. It authenticates the request and matches its live challenge, verifies the holder's signed exact hash, issuer signature, holder signature, issuer/holder/nonce and policy, and atomically consumes the challenge. A legacy unbound VP and another authentic request with the same nonce but different signed bytes must fail without consuming the challenge.

No new schema or hosted endpoints. Existing unbound methods remain available for compatibility and **must not** be treated as strict binding. This is a private `herossidRequestSha256` claim, not a standardized JWT VC claim or independent third-party wallet interoperability. The operation does not prove live non-revocation, human consent, legal identity or any business/Agent authorization. The integrating verifier owns secure pin retention and must separately enforce status/revocation and issuer/holder trust policy before authorization.
